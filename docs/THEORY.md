# Теорія: LALR-аналіз, yacc/bison, конфлікти

Конспект до захисту. Приклади посилаються на файли проєкту.

## 1. Етапи трансляції

1. **Лексичний аналіз** (flex, `src/lexer.l`) — текст → потік токенів (`INT`, `ID`, `'+'`, `INT_LIT` …).
2. **Синтаксичний аналіз** (bison, `src/parser.y`) — токени → дерево. Парсер перевіряє, що
   програма належить мові, заданій контекстно-вільною граматикою.
3. **Семантичний аналіз** (`src/sema.c`) — те, що граматика не може перевірити: чи оголошена змінна,
   чи збігається кількість аргументів, які типи у виразів, чи `break` всередині циклу.
4. **Синтез**: інтерпретація дерева (`src/interp.c`) або генерація коду іншою мовою (`src/codegen_py.c`).

## 2. Лексер: як працює lex/flex

Кожне правило flex — це регулярний вираз + дія на C. flex:

* будує за всіма виразами НСА (недетермінований скінченний автомат, конструкція Томпсона),
* перетворює його в ДСА (побудова підмножин) і мінімізує,
* генерує `yylex()`, яка «проганяє» вхід через таблиці ДСА.

Правила вибору, коли підходить кілька виразів:

* **найдовший збіг** — `>=` розпізнається як `GE`, а не `>` і `=`; `intx` — як `ID`, а не `int`;
* **при однаковій довжині — правило, що вище у файлі** — тому ключові слова (`"int"`) стоять раніше за
  загальний `{L}({L}|{D})*` для ідентифікаторів.

Значення токена лексер кладе в `yylval` (тип — `%union` з парсера), текст — у `yytext`.
Стан `%x COMMENT` (start condition) — окремий «режим» лексера для багаторядкових коментарів.

## 3. Синтаксичний аналіз знизу вгору (LR)

LR-парсер — це **автомат зі стеком**. У стеку лежать стани (і разом з ними семантичні значення `$$`).
На кожному кроці парсер дивиться на стан на вершині стеку і **поточний токен (lookahead)** і бере дію
з таблиці **ACTION**:

| дія | що відбувається |
|---|---|
| **shift s** | токен кладеться в стек, перехід у стан s, читаємо наступний токен |
| **reduce A → α** | з вершини знімається \|α\| станів (знайдено *основу*, handle), потім за таблицею **GOTO**[стан, A] кладеться новий стан; виконується дія правила в `{ }` |
| **accept** | вся програма згорнута в стартовий символ |
| **error** | помилка, запускається відновлення через токен `error` |

LR-аналіз будує **праве виведення у зворотному порядку**: дерево росте знизу вгору,
вузол створюється в момент reduce. Саме це показує кнопка «Відтворити згортки» у веб-версії:
вузли з'являються в post-order — спочатку діти, потім батько.

Приклад для `x = a + 2 * b;` (спрощено):

```
стек                         вхід              дія
                             x = a + 2 * b ;   shift ID
ID                           = a + 2 * b ;     reduce expr → ID
expr                         = a + 2 * b ;     shift '='
expr =                       a + 2 * b ;       shift ID, reduce expr → ID
expr = expr                  + 2 * b ;         конфлікт? '+' сильніший за '=' → shift
expr = expr +                2 * b ;           shift INT_LIT, reduce
expr = expr + expr           * b ;             '*' сильніший за '+' → shift
expr = expr + expr * expr    ;                 ';' слабший → reduce expr → expr * expr
expr = expr + expr           ;                 reduce expr → expr + expr
expr = expr                  ;                 reduce expr → expr = expr
expr                         ;                 shift ';', reduce stmt → expr ';'
```

### LR(0)-пункти, closure, goto

**Пункт** (item) — правило з крапкою: `expr → expr . '+' expr` означає «вже бачили `expr`, чекаємо `+`».
Стан автомата — множина пунктів.

* **closure(I)**: якщо в I є `A → α . B β`, додаємо всі `B → . γ` (якщо чекаємо B — можемо почати будь-яке правило для B).
* **goto(I, X)**: беремо пункти, де після крапки стоїть X, зсуваємо крапку, робимо closure.
* Канонічна сукупність станів — усі множини, досяжні з `closure({S' → . S})`.

### SLR(1), LR(1), LALR(1)

* **LR(0)** — reduce виконується незалежно від наступного токена. Майже для жодної реальної мови не підходить.
* **SLR(1)** — reduce `A → α .` тільки якщо lookahead ∈ FOLLOW(A). Просто, але FOLLOW — грубе наближення.
* **LR(1) (канонічний)** — у кожному пункті зберігається свій lookahead: `[A → α . , a]`.
  Найпотужніший, але станів дуже багато (для C — тисячі).
* **LALR(1)** — беремо стани LR(1) і **зливаємо ті, що мають однакове ядро** (однакові пункти без lookahead-ів),
  об'єднуючи lookahead-и. Станів стільки ж, скільки в LR(0) (у нашій граматиці — 188), а потужність майже як у LR(1).

Що може зламатися при злитті: **нового shift/reduce конфлікту виникнути не може** (shift залежить тільки від ядра),
а **reduce/reduce — може**. Приклад — `docs/conflicts/4_lalr_vs_lr1.y`:

```
s : A e C | A f D | B f C | B e D ;   e : E ;   f : E ;
```

У LR(1) після `A E` маємо `[e → E., C]`, `[f → E., D]`, а після `B E` — `[e → E., D]`, `[f → E., C]`.
Ядра однакові, LALR зливає стани, і lookahead-и стають `{C, D}` для обох правил → reduce/reduce.

```
bison 4_lalr_vs_lr1.y                         # 2 reduce/reduce конфлікти
bison -Dlr.type=canonical-lr 4_lalr_vs_lr1.y  # 0 конфліктів
```

yacc використовує саме LALR(1), бо таблиці компактні, а граматики мов програмування майже завжди LALR(1).
Bison за потреби вміє ще IELR(1) і канонічний LR(1) (`%define lr.type`).

## 4. Як працює yacc/bison

Файл `.y` має три частини, розділені `%%`:

```
%{ код на C, що йде на початок parser.c %}
оголошення: %token, %union, %type, %left/%right/%precedence, %start
%%
правила граматики з діями { ... }
%%
допоміжний код на C (yyerror, ...)
```

* `%token INT ID` — термінали; bison присвоює їм номери і записує в `parser.h`, який підключає лексер.
* `%union { ... }` — тип семантичного значення `YYSTYPE`; `%token <s> ID`, `%type <n> expr` — яке поле union
  використовує символ.
* У дії `$$` — значення лівої частини, `$1, $2 …` — значення символів правої частини.
  Наприклад, `expr '+' expr { $$ = binop("+", $1, $3); }` будує вузол AST.
* `yyparse()` в циклі викликає `yylex()`, робить shift/reduce за таблицями і викликає дії при кожному reduce.
* Таблиці ACTION/GOTO у згенерованому `parser.c` стиснені: `yypact`, `yytable`, `yycheck`, `yydefact`, `yypgoto`, `yydefgoto`.
  Для багатьох станів є дія «за замовчуванням» (`$default reduce`), щоб не зберігати повний рядок таблиці.
* Звіт про автомат: `bison --report=all` → `build/parser.output` (всі стани, пункти, переходи і як розв'язані конфлікти).
* **Помилки**: при неможливій дії викликається `yyerror`. Спеціальний токен `error` у правилах
  (`stmt : error ';'`) дозволяє відновитися: парсер знімає стани зі стеку, поки не знайде той, де можна
  зробити shift `error`, потім пропускає токени до `;`. `yyerrok` — сказати, що відновлення завершено.
  Тому `examples/errors/syntax_error.c` повідомляє кілька помилок, а не лише першу.

## 5. Конфлікти і як їх розв'язувати

**Конфлікт** — у клітинці таблиці ACTION виявилось більше однієї дії. Причина — граматика неоднозначна
або не є LALR(1).

* **shift/reduce**: можна і зсунути токен, і згорнути правило. За замовчуванням bison обирає **shift**.
  Класичний приклад — висячий else (`docs/conflicts/2_dangling_else.y`):
  `if (a) if (b) x; else y;` — після `if (b) x;` бачимо `else`: згорнути внутрішній if (else піде до зовнішнього)
  чи зсунути (else до внутрішнього)? Shift дає правильну для C поведінку.
* **reduce/reduce**: можна згорнути за двома різними правилами (`docs/conflicts/3_reduce_reduce.y`).
  bison обирає **правило, що раніше записане** у граматиці. Це майже завжди означає помилку в граматиці,
  її треба переписати.

`bison -Wcounterexamples` показує конкретний рядок, який можна розібрати двома способами (`make conflicts`).

### Пріоритети й асоціативність

Замість переписування граматики виразів на рівні (`expr → expr + term`, `term → term * factor` …)
yacc дозволяє лишити її неоднозначною і задати пріоритети:

```
%right '=' ADD_ASSIGN ...      ← найнижчий
%right '?' ':'
%left OR
%left AND
%left EQ NE
%left '<' '>' LE GE
%left '+' '-'
%left '*' '/' '%'
%precedence UNARY
%precedence INC DEC            ← найвищий
```

* Пріоритет **токена** — номер рядка, де він оголошений (нижче = сильніше).
* Пріоритет **правила** — пріоритет його останнього термінала, або заданий явно `%prec`.

При shift/reduce конфлікті між правилом R і токеном t:

1. prec(t) > prec(R) → **shift**; prec(t) < prec(R) → **reduce**;
2. рівні: `%left` → reduce, `%right` → shift, `%nonassoc` → помилка (`a < b < c` було б заборонено);
3. `%precedence` — тільки пріоритет, без асоціативності (якщо до асоціативності не дійде, bison не попереджає).

Приклади з нашої граматики:

* `a - b - c`: після `expr - expr` бачимо `-`; пріоритети рівні, `%left` → reduce → `(a - b) - c`.
* `a = b = c`: `%right` → shift → `a = (b = c)`.
* `-a * b`: правило `'-' expr %prec UNARY` сильніше за `*` → reduce → `(-a) * b`.
  Без `%prec` правило мало б пріоритет `'-'` (як бінарний мінус), і вийшло б `-(a * b)`.
* `(double)a / b`: cast теж `%prec UNARY` → `((double)a) / b`, як у C.
* `x++` після `-`: `INC` сильніший за `UNARY` → shift → `-(x++)`.
* Висячий else: `IF '(' expr ')' stmt %prec LOWER_THAN_ELSE`, а `ELSE` оголошений вище → shift.
  У `build/parser.output`:

```
   46 stmt: IF '(' expr ')' stmt .  [...]
   47     | IF '(' expr ')' stmt . ELSE stmt

    ELSE  shift, and go to state 181
    $default  reduce using rule 46 (stmt)

    Conflict between rule 46 and token ELSE resolved as shift (LOWER_THAN_ELSE < ELSE).
```

У нашій граматиці таким чином розв'язано 573 потенційні конфлікти, і bison не видає жодного попередження.
Якщо конфлікти свідомо залишають, кількість фіксують через `%expect N`.

## 6. AST і семантика

Дерево розбору (parse tree) містить усі нетермінали і дужки; **AST** — тільки суть: `(a + b) * c` дає
`BinOp[*](BinOp[+](a, b), c)`, дужок у дереві немає — їх «запам'ятала» структура.
AST будується в діях правил: кожен reduce створює вузол з дітей `$1, $3, …`.

Семантичний аналіз (`sema.c`):

* **таблиця символів** — стек областей видимості; новий рівень для кожного `{ }` і для `for (int i…)`;
* кожна змінна отримує **slot** (номер комірки у фреймі функції) — інтерпретатору не треба шукати імена;
* **виведення типів** знизу вгору: `int + double → double`, порівняння → `int`, `%` тільки для цілих;
* перевірки: неоголошені змінні, повторні оголошення, кількість/типи аргументів, lvalue в присвоєнні,
  `return` з/без значення, `break`/`continue` поза циклом.

## 7. Інтерпретатор

Рекурсивний обхід дерева: `eval(вузол)` для виразів, `exec(вузол)` для операторів. `exec` повертає статус
`NORMAL / BREAK / CONTINUE / RETURN` — так реалізовано керування потоком без `goto`.
Виклик функції створює новий фрейм (масив слотів), аргументи обчислюються в старому фреймі.
`&&` і `||` ліниві, як у C. Помилки виконання (ділення на 0, вихід за межі масиву, дуже глибока рекурсія)
повідомляються з номером рядка.

## 8. Генерація коду на Python

| проблема | рішення |
|---|---|
| `7 / -2` у C = `-3`, у Python `7 // -2 = -4` | хелпери `_idiv`, `_imod` (округлення до нуля) |
| присвоєння і `++` всередині виразу | оператор `:=`: `arr[((i := i + 1) - 1)] = 10` |
| `++` на елементі масиву у виразі | хелпери `_set`, `_post` |
| `for (;;)` немає в Python | `for i in range(...)`, якщо безпечно; інакше `while` |
| `continue` у `for` → у `while` пропустився б крок | прапорець `_firstN`, крок виконується на початку ітерації |
| `do-while` немає | `while True: ... if not cond: break` |
| `a < b` у C — число 0/1 | у числовому контексті `int(a < b)`, в умові — просто `a < b` |
| `a < b < c` у Python — ланцюжок | дужки: `int(a < b) < c` |
| блоки `{}` не створюють область видимості | sema дає унікальні імена: `v`, `v_2` |
| імена C, що є ключовими словами Python | `print` → `print_`, `lambda` → `lambda_` |
| `double` → `int` при присвоєнні | `int(...)` (відкидає дробову частину, як C) |
| `printf("%ld\n", x)` | `print("%d" % x)` — модифікатори довжини прибираються |

Пріоритети операцій Python враховуються, тож зайвих дужок генератор не ставить.

## 9. Можливі питання

**Чому bison, а не рекурсивний спуск?** Рекурсивний спуск — це LL(1), він не працює з ліворекурсивною
граматикою (`expr → expr + term`) і потребує ручного кодування. LALR будується автоматично і приймає ширший клас граматик.

**Чим LALR(1) відрізняється від LR(1)?** LALR зливає стани LR(1) з однаковим ядром. Станів набагато менше,
але можуть з'явитися reduce/reduce конфлікти (приклад вище). Shift/reduce від злиття не з'являються.

**Що буде без `%left '+' '-'`?** Shift/reduce конфлікти в кожному стані виду `expr op expr .`; bison обере shift,
і `a - b - c` розбереться як `a - (b - c)` — неправильно.

**Чому shift за замовчуванням?** Це дає правильну поведінку для висячого else і для правоасоціативних операцій,
а reduce/reduce означає справжню помилку в граматиці.

**Як парсер знає, що робити?** Тільки за станом на вершині стеку і одним токеном попереду — це і є «(1)» в LALR(1).

**Що таке основа (handle)?** Підрядок на вершині стеку, що збігається з правою частиною правила, згортка якого
є кроком правого виведення навпаки.

**Скільки станів у твоєму автоматі?** 188, правил 102 (див. `build/parser.output`).

**Як працює відновлення після помилки?** Правила з токеном `error` (`stmt : error ';'`): парсер знімає стани,
доки не зможе зсунути `error`, потім пропускає вхід до `;`.

**Як перевіряли коректність?** `make test`: кожну програму компілює gcc, і вивід порівнюється з інтерпретатором
і згенерованим Python — мають збігатися байт у байт.
